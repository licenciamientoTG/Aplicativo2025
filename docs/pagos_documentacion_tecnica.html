Pago a Proveedores — Documentación técnica

Módulo /payment/ del aplicativo TotalGas · Abastos / Tesorería / Contabilidad · Última actualización: 22 de julio de 2026

Este documento sustituye al docs/manual_tecnico_pagos_proveedores.md (febrero 2026), que describe el flujo cuando aún vivía en supply.php con autorización multinivel. Ese manual quedó obsoleto tras la migración al controlador dedicado payment.php. Para los diagramas de proceso ver docs/pagos_flujo_procesos.html.

1. Propósito

El módulo administra el ciclo completo de cuentas por pagar a proveedores de combustible y servicios: importación de documentos de compra desde las 40+ estaciones (ControlGas), creación de requisiciones de pago, autorización de Tesorería, generación de layouts bancarios (Santander / Banorte), registro y conciliación de pagos con comprobantes, anticipos con saldo, notas de crédito / cargo con CFDI, y agrupación contable para archivo físico.

2. Componentes

ComponenteTecnologíaResponsabilidad
Estaciones (ControlGas) SQL Server local por estación (192.168.2.101 – 192.168.40.101) Origen de los documentos de compra (DocumentosC). Fechas en serial ControlGas (días desde 1899-12-31).
ApiER Django REST (Python), http://192.168.0.109:82 Endpoints de consulta paralela vía OPENQUERY: documentos de compra por estación, facturas base, estadísticas. Es la fuente de las tablas de "documentos disponibles".
AplicativoPhp PHP MVC + Twig, IIS Controlador Payment (_assets/controllers/payment.php, ~7,300 líneas), 14 modelos, vistas views/payment/*.html, JS _assets/js/payment.js y authorize_payments.js.
Base central TG SQL Server 192.168.0.6 Todas las tablas del circuito de pago (ver §5) + FacturasRecibidas (CFDI descargados de correo) + Proveedores.
SG12 SQL Server 192.168.0.6 Catálogos regionales: Empresas, Gasolineras.
Bancos Portales Santander / Banorte Reciben los layouts de dispersión generados por el módulo; emiten los comprobantes PDF que después se concilian.

7. Permisos y seguridad

Mecanismo: authorized($permission_id) (_assets/classes/php_functions.php) revisa los permisos de la sesión. index.php solo valida sesión activa — toda la autorización granular vive en cada método del controlador. Los checks Twig en las vistas solo ocultan botones (cosméticos).

PermisoRolAcciones con check activo en backend
66Abastos update_payment_fields, send_to_payments (o token CRON), notas de crédito (preview / guardar / aplicar), catálogo de cuentas bancarias.
68Tesorería Autorización y ejecución de pagos, desautorizar, aplicar/pagar anticipos, conciliación de comprobantes.
69Eliminar pagosdelete_payment.
70Contabilidadauto_group_accounting (o token CRON).
Brechas conocidas (auditoría 2026-07-03):
  • Sin check de permiso en backend (solo sesión): generate_payment, add_invoice_to_payment, remove_invoice_from_payment, add_invoices_bulk_to_payment, create_anticipo, payment_detail, undoBulkAuthorization, create_accounting_group, removeCreditNoteApplication, deleteCreditDebitNote, reset_test_data.
  • generate_santander_layout / generate_banorte_layout: el 68 solo se valida en la vista, no en el controlador.
  • resend_today_payments exige user_id === 6296 hardcodeado (frágil).
  • can_user_authorize() del modelo tiene comentado el check de nivel; la única defensa real es el authorized() del controlador.

8. Reglas de negocio clave

ReglaDetalle
Fechas ControlGas fch es serial de Excel (días desde 1899-12-31); dateToInt() en PHP produce el mismo valor. Nunca usar formato YYYYMMDD.
Fecha de vencimiento SIEMPRE = fecha de emisión + días de crédito (TG.dbo.Proveedores) ajustada a día hábil según reglas por proveedor (Lobo/Altos: sáb→vie, dom→lun; Tesoro/Premiergas/ MGC/Enerey: sáb→lun, dom→lun). Nunca usar fechaVto del documento.
Total de la factura El total mostrado y pagado sale de FacturasRecibidas (UUID = satuid); el total ControlGas es fallback y se marca en rojo.
Remisiones sin satuid Documentos sin CFDI: no se agregan a pagos y siempre aparecen en Facturas Vencidas (no filtrar por satuid en invoices_due_table).
Neto autorizado authorized_amount = total − anticipos − NC + notas de cargo, calculado al autorizar y ajustado si se aplica una nota después. Las consultas de pago NO vuelven a restar NC (evita doble descuento, caso req. 1271).
NC requiere factura Aplicaciones de nota con invoice_id NULL dejan facturas en Parcial y requisiciones abiertas (caso req. 96) — el flujo actual lo exige.
Soft-delete Facturas de requisición nunca se borran físicamente (FK de anticipos); todos los joins — incluidos los de ApiER — filtran is_deleted = 0.
Candado contable Requisición con accounting_group_id no admite modificar facturas (assert_payment_not_grouped()).
Bancos por empresa Banorte: emp_cod 1, 10, 17, 18, 21, 23 · Santander: 16, 19, 20 (hardcode en PaymentRequestInvoicesModel / banco_por_emp_cod()).
